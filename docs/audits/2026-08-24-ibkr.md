## Findings P0 (corrigés)

### P0-1: TcpIbkrGatewayClient fabriquait des fills/positions/account fantômes (A)
**Avant:** `TcpIbkrGatewayClient` déléguait silencieusement à un `StubIbkrGatewayClient` in-memory (account $100k, fills à 1.10) → le runtime "trader" sans jamais toucher IBKR.
**Après:** les méthodes `placeMarketOrder`, `fetchAccountSummary`, `fetchOpenPositions` lèvent `UnsupportedOperationException` avec message de migration explicite (EClientSocket reqIds/placeOrder, reqAccountUpdates, reqPositions). Le stub reste réservé aux tests unitaires.
**Fichier:** `trading-data/.../ibkr/TcpIbkrGatewayClient.java`

### P0-2: IbkrBroker.submitOrder() fabricait un fill synchrone (A)
**Avant:** `order.fill()` + `emit(BrokerEvent.fill(...))` immédiatement après placeMarketOrder → fill price inventé (order.price()), corruption du PnL/equity.
**Après:** retour `OrderSubmitResult.filled(orderId)` SANS fill; le fill arrive via callback async `IbkrExecution` (execDetails/orderStatus). Nouveau record `IbkrExecution` + `addExecutionListener` sur `IbkrGatewayClient`; `IbkrBroker.onExecution` matche par clientTag (order.id()) et brokerId, puis émet le vrai `BrokerEvent.fill`.
**Fichiers:** `IbkrBroker.java`, `IbkrGatewayClient.java`, `IbkrExecution.java` (nouveau), `StubIbkrGatewayClient.java` (simule callback async)

### P0-3: IbkrBroker.cancelOrder() était un fake "CANCELLED" (A)
**Avant:** `cancelOrder` émettait un event CANCELLED et retournait `filled` sans rien annuler au broker → kill switch/liq sans effet, faux sentiment de sécurité.
**Après:** retour `OrderSubmitResult.rejected("IBKR order cancellation not implemented...")` — le caller (kill switch) doit traiter l'échec et escalader, pas supposer l'annulation.

### P0-4: IbkrAccountCache fabriquait un compte sain par défaut (A)
**Avant:** métriques manquantes → defaults $100k NetLiquidation, buying power ×4, 3 day-trades → sizing/margin guards voyaient du capital fantôme.
**Après:** fail-closed: NetLiquidation 0.0, AvailableFunds 0.0, BuyingPower 0.0, DayTradesRemaining 0.0 → guards refusent de trader.
**Fichier:** `IbkrAccountCache.java`

### P0-5: Bracket order: parent dans le groupe OCA (A)
**Avant:** l'entrée (parent) partageait le groupe OCA des SL/TP → au fill du parent, l'OCA type 1 ("cancel with block") annulait les SL/TP → position nue.
**Après:** parent standalone, SL/TP mutuellement cancelling dans le même OCA group, liés au parent via parentId.
**Fichier:** `IbkrBracketOrderRouter.java`

### P0-6: Margin rejection 201 traité à tort comme marge (A)
**Avant:** tout code 201 = "insufficient margin" → pause stratégie; or 201 couvre aussi prix invalide, contrat inconnu.
**Après:** `isMarginRejection(201|202, message)` matche le texte (margin/insufficient/cash/funds/buying power/available).
**Fichier:** `IbkrOrderExecutionManager.java`

### P0-7: Contrat futures résolu avec mauvais exchange/expiry (A)
**Avant:** exchange="CME", lastTradeDate=YYYYMM → ambigu, IBKR peut rejeter.
**Après:** exchange="GLOBEX", lastTradeDate=YYYYMMDD (3rd-Friday expiry de CmeFuturesCalendar).
**Fichier:** `IbkrContractResolver.java`
