| D1 | 2026-10-29 | The engine is a **config-driven single-strategy runner**, not a lifecycle platform (no promotion state machine, no registry UI, no multi-account). | John: the value is "one description, two modes". Everything else is gold-plating with no second consumer. | accepted |
| D2 | 2026-10-29 | `prd-ibkr-futures-2026-06-15` is **superseded** as the authority for futures execution; its broker lessons are absorbed, its MES-only and desktop-UI scope are dropped. | It was marked "finalized" in June 2026 and the live half was never delivered. | D3 | 2026-10-29 | The existing **75 `Run*.java` coexist** with the config engine; each is deleted only once its config equivalent passes the F2 parity test. | Deleting them in one pass destroys the only record of how each was configured. | accepted |
| D4 | 2026-10-29 | Strategies keep the existing **`Strategy` contract returning `Order`** (which already carries `stopLoss`, `takeProfit`, `ocaGroup`, `parentId`). No new `Signal` type. | Introducing `Signal` would rewrite 32 strategies for no capability gain (Winston's intent is preserved: `Order` is a value object, only the broker executes). | accepted |
| D5 | 2026-10-29 | **IBKR stop support ships first**, inside this PRD, not as a follow-up epic. | `IbkrBroker.submitOrder` silently drops `stopLoss`/`takeProfit` (`IbkrBroker.java:134`), so every live entry is a naked position today. | accepted |
| D6 | 2026-10-29 | Runs are declared in **`config/runs/<strategy>-<symbol>-<mode>.json`**, validated at startup. | JSON is already the project's config language; an unknown strategy, symbol or mode must refuse to start. | accepted |
| D7 | 2026-10-29 | **One container per run config**, as today. | Preserves the deployed lane's isolation, the reconciler's assumptions, and the guard against two runners on one instrument. | accepted |
| D8 | 2026-10-29 | A strategy may run live only if its config **names the backtest that validated it**, or sets `unvalidated: true` (paper only). | Makes "the thing I tested is the thing that trades" enforceable instead of aspirational (F5). | accepted |
| D9 | 2026-10-29 | Delivery order: **Phase 1 = F3 (`tech-spec` 46-7..46-12)** first to establish the IBKR MGC paper lane with venue stops, then **Phase 2 = F1/F2/F4/F5** (unified JSON runner, backtest parity, JSONL fill log, cost validation gate). | Proves the live IBKR execution path and protective stop first before unifying the config entrypoint across modes. | accepted |
| D10 | 2026-10-29 | Unified fill log (F4) is stored as **JSON Lines (`.jsonl`)** under `data-futures/fills/<strategy>-<symbol>-<mode>.jsonl`. | Append-only, zero DB coupling, directly consumable by a CLI comparison report for both backtest and paper/live runs. | accepted |
| D11 | 2026-10-29 | For historical parity and A1/A2 verification, **`.bars` files (2003–2026) are authoritative**; any divergence with the 2026 CSV is measured and documented in the report. | Guarantees format consistency across the full 24-year MGC M30 series while making the CSV vs `.bars` delta explicit. | accepted |
| D12 | 2026-10-29 | **Single `ib-gateway` instance on the VPS**; both VPS and Mac runners/tests connect via configurable `IBKR_HOST`/`IBKR_PORT` and distinct `IBKR_CLIENT_ID`s (never launching a second competing `ib-gateway` session on the same IBKR user). | Prevents IBKR competing-session disconnects while allowing execution and verification from both Mac and VPS. | accepted |
